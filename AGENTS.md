# AGENTS.md

## Область действия

Этот файл действует для всего репозитория. Если в отдельном каталоге появится свой
`AGENTS.md`, он может уточнять правила только для этого поддерева.

Перед изменениями изучи затронутый код, ближайшие тесты и `git status`. Не перезаписывай
чужие незакоммиченные или untracked-файлы и не делай попутных массовых исправлений.

## Что это за проект

ExpoSlides — Python pre-MVP для локального пайплайна:

```text
PPTX-шаблон -> Presentation JSON -> LLM-контент -> итоговый PPTX
```

Корневой CLI `python -m exposlides` оркестрирует три файловых этапа в отдельных процессах:

1. `parsing-service` разбирает PPTX в подробную Pydantic-модель.
2. `content-service` анализирует исходный текст, планирует слайды, генерирует контент
   placeholders и валидирует его через LangGraph.
3. `builder-service` упорядочивает выбранные слайды по плану и заменяет в них текст.

Это пока не сетевая микросервисная система. API gateway, Kafka, protobuf, file/evaluation/
vision services, Docker и Compose — заготовки или roadmap. Не реализуй и не описывай их как
работающие, если текущая задача явно этого не требует.

## Источники истины

При расхождениях используй следующий приоритет:

1. исполняемый код и тесты;
2. `pyproject.toml`, `uv.lock`, `.python-version`;
3. `README.md` и `evals/README.md`;
4. `PROJECT_REVIEW.md`, `DEVDOCK.md`, `TODO.txt`.

Последняя группа содержит датированные снимки и планы и может отставать от кода. Например,
минимальный builder уже существует, хотя часть обзора всё ещё называет его отсутствующим.
Если поведение меняется, обновляй относящуюся к нему документацию, но не переписывай roadmap
без необходимости.

## Технологии и окружение

- Python 3.12 из `.python-version`; поддерживаемый диапазон — `>=3.11,<3.14`.
- Единственный основной менеджер окружения и зависимостей — `uv`.
- Корневые `pyproject.toml` и `uv.lock` авторитетнее service-level `requirements.txt`.
- Основные библиотеки: Pydantic v2, `python-pptx`, `lxml`, LangGraph и GigaChat.
- Проверки: pytest и Ruff; type checker и CI пока не настроены.

Первичная настройка из корня:

```bash
uv sync --locked
```

Не используй системный `python`/`pip` и не создавай отдельные окружения внутри сервисов.
Если меняются зависимости, обнови корневые `pyproject.toml` и `uv.lock`, затем проверь:

```bash
uv lock --check
```

Service-level `requirements.txt` — незакреплённые списки для будущей отдельной установки.
Обновляй их только вместе с задачей на соответствующий standalone-сервис.

## Карта репозитория

| Путь | Назначение |
| --- | --- |
| `exposlides/` | Корневой CLI, изоляция этапов и финальная проверка PPTX |
| `services/parsing-service/app/` | PPTX-парсер и полная модель презентации |
| `services/content-service/app/` | LLM-клиент, промпты, LangGraph, grounding и валидация |
| `services/builder-service/app/` | Сборка PPTX и замена текста placeholders |
| `tests/` | Офлайн-тесты парсера, content pipeline и eval scorer |
| `evals/` | Фиксированные сценарии и детерминированный scorer качества |
| `services/*/todo.txt`, `kafka/`, `proto/` | Нереализованные заготовки |
| `README.md` | Короткий поддерживаемый вход в проект |
| `PROJECT_REVIEW.md`, `DEVDOCK.md` | Обзор ограничений и долгосрочный план |

Во всех трёх сервисах пакет называется `app`. Не добавляй несколько service roots в один
Python-процесс: модули столкнутся в `sys.modules`. Тестовый fixture `service_importer` в
`tests/conftest.py` специально очищает `app` между импортами. Сервисы запускай из их
собственных каталогов через `python -m app.main` под `uv`.

## Межсервисный контракт

Контракт пока передаётся файлами и продублирован в нескольких сервисах. Сохраняй следующие
инварианты:

- индексы слайдов — целые, начинаются с 1;
- `generated_content.json.content` индексируется исходным `slide_index`;
- ключ placeholder в generated content — строковый `placeholder_idx`, при его отсутствии имя;
- один `template_slide_index` сейчас можно использовать только один раз;
- content-service обрабатывает только текстовые элементы с `placeholder_type`; обычные text
  boxes в генерацию не попадают;
- builder сохраняет порядок ключей generated content, но не создаёт новые слайды и не умеет
  повторно использовать один образец;
- строки list-placeholder записываются отдельными абзацами; content-service не должен
  добавлять ручные дефисы, bullets или нумерацию поверх оформления PPTX-шаблона;
- builder отклоняет исключение слайдов, на которые ссылаются PowerPoint custom shows или
  sections, чтобы не оставить скрытые слайды или повреждённые presentation-level ссылки;
- `max_length` в content-service — приблизительная оценка по длине исходного текста, а не
  гарантия отсутствия визуального переполнения.

Изменение формата нельзя делать только в одном месте. Проверь и синхронно обнови как минимум:

- `services/parsing-service/app/models/presentation.py`;
- `services/content-service/app/utils/presentation_parser.py`;
- `services/content-service/app/models/`;
- `services/builder-service/app/models/`;
- затронутые тесты, eval fixtures и документацию.

Для миграции контракта предпочитай явную совместимость или понятную ошибку валидации, а не
молчаливое отбрасывание неизвестных данных.

## Локальный файловый сценарий

Основной запуск выполняй из корня; входные PPTX/TXT передаются явно, промежуточные файлы
создаются в уникальном временном каталоге:

```bash
uv run python -m exposlides \
  --template /path/to/template.pptx \
  --script /path/to/script.txt \
  --output /path/to/result.pptx
```

Для реального запуска нужен локальный `services/content-service/.env` с LLM-конфигурацией.
Прямые точки входа ниже полезны для изоляции конкретного этапа.

### 1. Парсинг

```bash
cd services/parsing-service
uv run python -m app.main
```

Требуется `test.pptx`; результат — `output.json` в текущем каталоге.

### 2. Генерация контента

```bash
cd services/content-service
uv run python -m app.main
```

Требуются `template.json`, `script.txt` и LLM-конфигурация; результат —
`generated_content.json`. `.env` ищется относительно текущего каталога, поэтому не запускай
этот entry point из корня без явных переменных окружения.

### 3. Сборка

```bash
cd services/builder-service
uv run python -m app.main
```

Требуются `template.pptx`, `template.json` и `generated_content.json`; результат —
`result.pptx`.

Не предлагай `docker compose up`: Dockerfiles и `docker-compose.yaml` пока пусты. Не называй
ручную цепочку полноценным end-to-end тестом, если реальный PPTX не был создан и повторно
открыт.

## Секреты и внешние вызовы

- Никогда не читай, не печатай и не коммить существующий `services/content-service/.env`.
- Не добавляй реальные ключи в `.env.example`, тесты, логи, fixtures или документацию.
- Все автоматические тесты обязаны работать без сети и без LLM API. Подменяй
  `llm_client.generate_json`, `generate_json_with_schema` или низкоуровневый `client.chat`.
- Реальный вызов GigaChat делай только когда задача явно требует интеграционной проверки и
  пользователь предоставил конфигурацию.
- Текущий LLM-клиент отключает проверку TLS (`verify_ssl_certs=False`). Это известный долг,
  а не допустимый production-паттерн; не копируй его в новый код.
- По умолчанию используется `LOG_LEVEL=INFO`. При явном `DEBUG` в лог попадают промпты,
  исходный текст и сырой ответ. Не прикладывай
  такие логи целиком и не добавляй секреты в сообщения логирования.

## Правила разработки

### Общие

- Соблюдай Ruff: длина строки 100, правила `E4`, `E7`, `E9`, `F`, `I`.
- Используй аннотации типов и API Pydantic v2 (`model_validate`, `model_dump`,
  `model_validate_json`), а не совместимость с Pydantic v1.
- Для путей используй `pathlib.Path`, для текстовых файлов явно указывай UTF-8, для русского
  JSON — `ensure_ascii=False`.
- Идентификаторы и поля контрактов оставляй на английском. В существующих пользовательских
  сообщениях, логах и docstrings сохраняй русский язык и стиль соседнего кода.
- Не меняй публичный async-интерфейс без причины. Блокирующую работу с PPTX и файлами выноси
  через `asyncio.to_thread`, когда она вызывается из async pipeline.
- Не форматируй весь репозиторий ради локального изменения и не запускай глобальный
  `ruff --fix` без отдельной задачи.

### Parsing service

- Сохраняй стабильные и уникальные element IDs между одинаковыми запусками.
- Не ломай 1-based индексы слайдов, связь slide/layout и чтение theme через related part.
- Для regression fixtures предпочитай создавать минимальный PPTX программно в `tmp_path`,
  как в `tests/test_pptx_parser.py`, вместо добавления бинарников.
- Любое новое извлечение должно быть отражено в Pydantic-модели и тесте сериализованного
  результата.

### Content service

- Каноническое состояние графа находится в `app/models/graph_state.py`;
  `app/graph/state.py` пока пуст и не должно становиться вторым источником моделей.
- При `GenerationSettings.strict_user_mapping=True` все слайды из пользовательской разметки
  должны попасть в план; ключи слайдов/placeholders и значения проверяются до вызова LLM.
- Не ослабляй grounding: числа, проценты, даты и неподтверждённые сравнения должны проверяться
  на каждом этапе.
- Невалидный ответ LLM должен приводить к типизированной ошибке после ограниченного retry, а
  не превращаться в пустую модель или частично валидный результат.
- При content retry сохраняй уже валидные слайды и передавай проблемному слайду только
  относящиеся к нему плюс глобальные ошибки.
- Изменение prompt, JSON Schema, retry или validation сопровождай unit-тестом с fake LLM.
- Если изменение заявлено как улучшение качества, обнови или запусти сопоставимый сценарий из
  `evals/`; scorer дополняет, но не заменяет редакторскую и визуальную оценку.

### Builder service

- Операции с приватными XML-структурами `python-pptx` (`_sldIdLst`, relationships и т.п.)
  изолируй и покрывай тестами: ошибка может создать открывающийся, но повреждённый файл.
- Сохраняй стили, связи и порядок слайдов; не считай успешный `save()` достаточной проверкой.
- Для изменения builder добавь программно создаваемый PPTX fixture, собери результат, снова
  открой его через `python-pptx` и проверь число/порядок слайдов, текст и нужные стили.
- `app/utils/clone.py` сейчас не подключён к pipeline; не описывай клонирование как готовую
  возможность.

## Проверки

Минимальный набор из корня:

```bash
uv run pytest
uv run ruff check .
```

Полезные целевые команды:

```bash
uv run pytest tests/test_pptx_parser.py
uv run pytest tests/test_generation_pipeline.py tests/test_content_quality.py
uv run pytest tests/test_generation_evals.py
uv run pytest tests/test_pptx_builder.py tests/test_end_to_end.py tests/test_cli.py
uv run ruff check path/to/changed_file.py
```

Полные pytest и Ruff должны проходить. Сначала сними baseline и не маскируй новые ошибки
старыми. `ruff format --check` пока не является настроенным gate и требует массового
форматирования, поэтому не применяй его ко всему репозиторию попутно.

Требования по области изменения:

| Изменение | Обязательная проверка |
| --- | --- |
| Parser/model | `test_pptx_parser.py` и полный pytest |
| Prompt/LLM/graph/validation | generation/content tests и полный pytest |
| Eval cases/scorer | `test_generation_evals.py` и запуск scorer на нужном case |
| Builder | `test_pptx_builder.py`, повторное открытие PPTX, полный pytest |
| Root CLI / orchestration | `test_cli.py`, `test_end_to_end.py` и полный pytest |
| Dependencies/межсервисный контракт | `uv lock --check`, полный pytest и Ruff |
| Только документация | проверить пути, команды и отсутствие устаревших утверждений |

## Gitignore и артефакты

Не коммить `.env`, ключи, `.venv`, кэши, логи, локальные PPTX и сгенерированные JSON/TXT.
Учти, что `.gitignore` широко исключает `*.pptx`, `*.json` и `*.txt`. Если задача требует
новый текстовый или JSON fixture, добавь узкое исключение для конкретного пути и проверь, что
файл действительно отслеживается. Не меняй широкие ignore-правила без отдельной причины.
`evals/generation_cases.json` — версионируемый исходник и не должен считаться generated-файлом.

## Definition of Done

Перед завершением задачи:

1. Проверь diff и отсутствие случайных изменений/секретов.
2. Добавь или обнови тесты для нового поведения; внешние вызовы должны быть замоканы.
3. Запусти целевые проверки, затем полный pytest и Ruff либо честно опиши baseline/blocker.
4. При изменении зависимостей проверь lock-файл; при изменении контракта синхронизируй все
   потребители.
5. При изменении PPTX-логики повторно открой созданный файл и проверь структуру.
6. Обнови README/evals docs, если изменились команды, конфигурация или наблюдаемое поведение.
7. В итоговом отчёте перечисли изменённые файлы и точные команды с их результатом; не заявляй
   проверки, которые не запускались.
