# ExpoSlides

ExpoSlides превращает PPTX-шаблон и текстовый сценарий в новую редактируемую презентацию.
Локальный pipeline последовательно разбирает шаблон, генерирует проверенный контент через
GigaChat и собирает итоговый PPTX.

## Быстрый старт: интерфейс в браузере

Команды ниже предназначены для терминала macOS или Linux. Нужны Git,
[uv](https://docs.astral.sh/uv/getting-started/installation/) и доступ к GigaChat API.
Проект использует Python **3.12** из `.python-version`; окружением управляет `uv`.
Для локального запуска достаточно Python-приложения: отдельная сборка frontend,
Node.js, Docker, Kafka и генерация gRPC-модулей не требуются.

### 1. Скачать проект и установить зависимости

Актуальная версия находится в ветке **`dev`**.

Если `uv` ещё не установлен, на macOS с Homebrew выполните `brew install uv`;
другие способы приведены в [инструкции uv](https://docs.astral.sh/uv/getting-started/installation/).

```bash
git clone --branch dev https://github.com/nebel310/ExpoSlides.git
cd ExpoSlides
uv python install 3.12
uv sync --locked
```

Все дальнейшие команды выполняйте из папки `ExpoSlides`, где находится `pyproject.toml`.

### 2. Настроить GigaChat

Один раз создайте локальный файл настроек:

```bash
cp -n .env.example services/content-service/.env
```

Откройте `services/content-service/.env` в текстовом редакторе и замените
`LLM_API_KEY=your-api-key` своим **ключом авторизации (Authorization key)** GigaChat API
([о ключе в документации GigaChat](https://developers.sber.ru/docs/ru/gigachat/api/reference/rest/post-token)).
Приложение передаёт его как `credentials`; краткоживущий `access_token` сюда не подходит.
Реальный ключ хранится только в этом локальном файле, который исключён из Git.
Команда `cp -n` сохраняет уже существующий файл настроек.

Для персонального доступа оставьте `LLM_SCOPE=GIGACHAT_API_PERS`. Если ваш доступ использует
другой scope, укажите его. Интерфейс по умолчанию использует `GigaChat-2-Pro`
через `LLM_FAST_MODEL` и `LLM_FAST_REPAIR_MODEL`; остальные значения можно оставить из примера.

### 3. Установить программы для просмотра слайдов

Чтобы видеть **цвета, картинки и оформление**, нужны
[LibreOffice](https://formulae.brew.sh/cask/libreoffice) и
[Poppler](https://formulae.brew.sh/formula/poppler).

macOS с Homebrew:

```bash
brew install --cask libreoffice
brew install poppler
```

Ubuntu / Debian:

```bash
sudo apt update
sudo apt install libreoffice poppler-utils
```

`pdftoppm` из Poppler должен быть доступен в `PATH`. LibreOffice ищется как `soffice`
или `libreoffice` в `PATH`, а на macOS также в `/Applications/LibreOffice.app`.
Без этих программ генерация и скачивание PPTX работают, но вместо изображений слайдов
отображается текстовая схема. Если установили их при работающем сервере, перезапустите его.

### 4. Запустить и открыть страницу

```bash
uv run python -m exposlides.web
```

Оставьте терминал открытым и перейдите в браузере на **[http://127.0.0.1:8765](http://127.0.0.1:8765)**.

1. Загрузите PPTX-шаблон с текстовыми заполнителями PowerPoint (placeholders).
2. Вставьте текст доклада или импортируйте `.txt` в UTF-8.
3. При необходимости ограничьте количество слайдов и нажмите «Создать презентацию».
4. После сборки просмотрите результат и скачайте PPTX.

Остановка сервера — **Ctrl+C** в его терминале. Перед остановкой скачайте результат:
файлы сессии хранятся временно и удаляются при завершении сервера.

### Повторный запуск и другой порт

После первоначальной настройки достаточно из корня проекта выполнить:

```bash
uv run python -m exposlides.web
```

Если порт 8765 занят:

```bash
uv run python -m exposlides.web --port 8766
```

Тогда откройте [http://127.0.0.1:8766](http://127.0.0.1:8766).
После изменения `.env` также перезапустите сервер.

## Запуск из командной строки

После той же установки и настройки GigaChat презентацию можно собрать без интерфейса:

```bash
uv run python -m exposlides \
  --template /path/to/template.pptx \
  --script /path/to/script.txt \
  --output /path/to/result.pptx \
  --generation-mode fast \
  --max-slides 5
```

Команда выполняет три этапа в отдельных процессах:

1. `parsing-service`: PPTX → `template.json`;
2. `content-service`: template JSON + script → `generated_content.json`;
3. `builder-service`: template PPTX + generated content → проверенный итоговый PPTX.

Локальный парсер использует модульный формат Presentation JSON `2.0.0`: типы полей
хранятся в `placeholder_kind`, текст — в `paragraphs[].runs[]`, тема — в `tokens.theme`.
Генератор и сборщик явно поддерживают этот формат и прежний JSON без версии либо с
`schema_version: "1.0.0"`; неизвестные версии отклоняются до генерации или сборки.
При чтении v2 тип `content` преобразуется во внутренний `OBJECT`, а текстовые фрагменты
собираются с сохранением границ абзацев. Индексы слайдов и ключи полей не меняются.
Прежний Python API `app.parsers.pptx_parser.PPTXParser` сохранён на отдельной модели v1;
активный CLI и сетевой parser-service используют `app.parsers.pptx.PPTXParser` v2.

Корневая команда передаёт content-service флаг `--cli`: локальная генерация не требует
Kafka. При прямом запуске `python -m app.main` из каталога content-service этот флаг нужно
указывать явно, иначе сервис запускается в сетевом режиме.

Для пакетной генерации добавьте `--generation-mode fast`. В этом режиме анализ и план
создаются одним запросом, а все выбранные слайды заполняются вторым. На весь запуск
разрешено по одной основной попытке исправления плана и текста слайдов. Исправление текста
выполняется отдельной короткой задачей группами до 16 полей, последовательно с учётом
лимита одновременных запросов API. Для него используется `LLM_FAST_REPAIR_MODEL`
(по умолчанию `GigaChat-2-Pro`).
Если анализ уже прошёл проверку, повтор плана сохраняет его и исправляет только слайды.
Ответ планировщика содержит объект `slides`, где ключи — уникальные индексы доступных
слайдов шаблона. Схема ограничивает допустимые ключи, их число и обязательные слайды;
повтор одного JSON-ключа отклоняется до разбора модели, без потери предыдущего значения.
Порядок ключей сохраняется, затем ответ переводится во внутренний список `SlidePlan`;
файловые контракты сервисов не меняются. При ответе в прежнем списочном формате
без пользовательской разметки повторный индекс образца можно заменить свободным
слайдом шаблона с тем же составом основных текстовых полей. Выбирается ближайший
по вместимости образец; тексты и ссылки на исходные блоки не меняются. Уже выбранные
слайды зарезервированы, новые слайды не создаются. Если совместимого образца нет,
план проходит обычное ограниченное исправление. После замены все проверки сохраняются.
Схема ответа ограничивает ссылки существующими блоками анализа; при строгой разметке
также задаёт минимальное число обязательных слайдов и общий максимум. Пустая разметка
конкретного слайда `{}` требует включить этот слайд, не фиксируя текст его полей.
Если в исходнике нет цифр, инструкции запрещают добавлять их в текст, включая нумерацию
разделов. Нативные строковые `pattern` не отправляются: в контрольных запусках они
вызывали таймауты провайдера. Факты проверяются программно на каждом этапе;
нарушения исправляются в пределах общего бюджета повторов. Числовые индексы слайдов
и блоков остаются допустимыми.
Перед проверкой плана приложение снимает однозначную нумерацию `1..N` в списках
и соседних заголовках, включая списки в одной строке через точки или стрелки.
Это локальное изменение оформления без дополнительного запроса к модели; слова,
пунктуация и ссылки на блоки сохраняются. Одиночные номера, нарушенные последовательности,
даты, количества и числа, встречающиеся в исходнике, остаются для обычной проверки фактов.
Та же обработка применяется к ответу на исправление плана и в автоматическом режиме.
При ошибках только длины модель получает задачу сокращения проверенного текста;
при смешанных ошибках она также сверяется с исходником. Корректные поля сохраняются;
проверки структуры, числовых фактов, списков, длины и порядка слайдов остаются обязательными.
Если после исправления остаются ошибки полей, выполняется один дополнительный этап:
модель предлагает три законченных варианта каждой подписи. При ошибке только длины
она сокращает готовый текст; при ошибке содержания использует проверенный план
вместо отклонённого ответа, чтобы не переносить выдуманные сведения в новые варианты.
Приложение выбирает самый длинный из вариантов, которые помещаются в поле
и сохраняют числовые факты и отрицания. Слова не обрываются; весь результат снова проходит
общую проверку, включая полноту обязательных фактов. Подходящие варианты всех групп
сохраняются. Для не более 16 оставшихся полей допускается ещё один короткий запрос
внутри общего лимита 240 секунд; корректные поля не генерируются повторно.
Если и этот запрос не помог, для короткого поля до 40 символов можно выбрать явную
тему перед двоеточием или тире: не более четырёх целых слов, дословно присутствующих
в исходнике. Допустим также целый технический термин вроде `LangChain` или `API`
из исходной подписи либо проверенного плана этого же слайда, если он встречается
в исходнике и помещается в поле. Сначала рассматривается заголовок, затем сообщение
и содержание этого слайда. Случайные слова и части составных слов не выбираются.
Также допустим целый короткий заголовок этого слайда, если он дословно встречается
в исходнике; отдельные случайные слова из предложений не выбираются.
Это допускается для проверенного текста без чисел, словесных количеств вроде «вдвое»
и отрицаний, включая «запрещён» и «недоступен». После смысловой ошибки разрешён тот же
выбор, если вход сокращения полностью заменён проверенным планом этого слайда;
отклонённая формулировка не используется как источник подписи.
Контекст с такими ограничениями не используется как источник термина. Различие
обычных и типографских кавычек не мешает сопоставить явную тему с исходником.
Такая обработка не требует
нового запроса к модели. Все остальные проверки остаются обязательными; если подходящего
текста нет, невалидный файл не публикуется. Итоговая ошибка сообщает текущую причину
остановки, не перечисляя уже устранённые ошибки предыдущих ответов.
Используется `LLM_FAST_MODEL` (по умолчанию `GigaChat-2-Pro`), отдельно от `LLM_MODEL`
стандартного режима. Модель можно переопределить переменной окружения. Более точный профиль
Pro выбран по контрольному прогону плотного шаблона из 15 слайдов; общий бюджет ожидания
остаётся прежним.
`LLM_FAST_API_TIMEOUT=120` ограничивает один запрос, `FAST_GENERATION_TIMEOUT=240` — весь
этап контента. Истечение времени завершает запуск ошибкой без частичного результата;
этот предел не является гарантией успешной генерации при любой нагрузке API.
Временные HTTP-ошибки 429/500/502/503/504, разрывы соединения и таймаут подключения
повторяются не более двух раз с задержками 1 и 2 секунды внутри того же таймаута запроса.
Ошибки авторизации и проверки TLS-сертификата не повторяются; таймаут ожидания ответа
тоже не запускает новый запрос. Закрытие сетевого клиента ограничено 5 секундами
и не отменяет уже проверенный результат или исходную ошибку генерации.
Быстрый клиент проверяет TLS через стандартные CA и официальный сертификат GigaChat,
описанный в [certificates/README.md](services/content-service/app/certificates/README.md).
Для собственного CA можно задать `GIGACHAT_CA_BUNDLE_FILE` в окружении запуска.
Без флага корневой CLI сохраняет режим `standard` с отдельной обработкой каждого слайда.

LLM-клиент восстанавливает распознаваемый шум перед целыми JSON-токенами, включая
числовые индексы блоков, и завершающие запятые вне строк. Содержимое строк не меняется.
Обрезанный или всё ещё невалидный ответ отклоняется после ограниченного числа попыток;
проверки схемы и фактов остаются обязательными.
Схема placeholder'ов запрещает пустые строки. При повторной попытке модель получает
отклонённый ответ вместе с ошибкой валидации, чтобы исправить конкретные значения.
При ошибке отдельного поля уже валидные значения сохраняются, а повторный запрос
ограничивается полями с ошибками. Итоговый объект снова проверяется по полной схеме.
Лимит длины передаётся GigaChat как текстовая инструкция, а не нативный `maxLength`,
который может обрывать слова. Клиент проверяет исходный лимит локально и при превышении
запрашивает короткую переформулировку. В быстром режиме планировщик и генератор получают
типы и вместимость полей; демонстрационные тексты, названия макетов и заметки
шаблона не передаются как материал доклада. Это уменьшает риск переноса имён и посторонних
утверждений из текста-образца. Стандартный режим по-прежнему использует примеры полей.
Генератор получает и анализ, и оригинальный сценарий. Лексическая проверка связности
требует не менее четырёх общих значимых слов и 30% совпадения лексики результата с
источником; она не требует переносить фиксированную долю слов длинного доклада на слайды.
Проверки числовых фактов и неподтверждённых сравнений выполняются отдельно и обязательны.
Отдельные проверки отклоняют буквальные служебные подписи вроде `FOOTER` и имена без
привязки к исходнику в полях с подсказкой «Имя докладчика» или примером полного имени.
Это узкие проверки
типичных ошибок шаблона, а не полная проверка всех именованных сущностей.
В стандартном режиме временные HTTP-ошибки 500/502/503/504 повторяются с задержкой в пределах
`LLM_RESPONSE_RETRIES`; ошибки авторизации повторно не отправляются.

Результат публикуется атомарно только после проверки ZIP-структуры, повторного открытия через
`python-pptx` и сверки количества слайдов. Существующий output не перезаписывается без
`--force`.

Чтобы сохранить промежуточные JSON и лог конкретного запуска:

```bash
uv run python -m exposlides \
  --template template.pptx \
  --script script.txt \
  --output result.pptx \
  --artifacts-dir artifacts
```

Каждый запуск получает отдельный каталог `artifacts/exposlides-*`. Без этого флага временные
файлы удаляются автоматически. Все параметры доступны через:

```bash
uv run python -m exposlides --help
```

## Локальный интерфейс

После настройки окружения запустите из корня:

```bash
uv run python -m exposlides.web
```

Откройте [ExpoSlides в браузере](http://127.0.0.1:8765). Другой порт можно задать через
`--port 8766`. Сервер слушает только `127.0.0.1`; это локальное рабочее окно, а не публичный
веб-сервис. Сборка frontend не нужна.
Новые генерации из интерфейса используют пакетный режим `fast`.

В интерфейсе можно:

- загрузить или перетащить PPTX до 25 МБ и просмотреть слайды с оформлением;
- вставить сценарий до 100 000 символов или импортировать `.txt` в UTF-8;
- ограничить максимальное количество слайдов в пределах шаблона;
- следить за этапами обработки, просмотреть готовые слайды и скачать проверенный PPTX;
- открыть встроенный пример из пяти слайдов без вызова LLM.

После загрузки приложение в фоне готовит изображения слайдов с фоном, картинками и
оформлением исходного PPTX. Они появляются в предпросмотре и миниатюрах; во время подготовки
можно вводить текст. Для рендера нужны LibreOffice (`soffice`) и Poppler (`pdftoppm`) в `PATH`.
Если они недоступны или не удалось отрисовать файл, интерфейс явно сообщает об этом и
показывает текстовую схему. Предпросмотр выполняется локально, без вызова LLM; шрифты и
некоторые эффекты могут отличаться от PowerPoint.

После успешной сборки просмотр автоматически переключается на готовый PPTX: его текст,
порядок, количество слайдов и изображения. Результат отрисовывается в той же фоновой
очереди, отдельно от шаблона; скачивание доступно сразу, без ожидания изображений.
При ошибке рендера показывается текст готовой презентации, а ссылка на скачивание
остаётся доступной. Перезагрузка страницы восстанавливает просмотр завершённого задания
в пределах работающей сессии сервера.

Итоговый файл сохраняет оформление исходного шаблона. Для генерации используются CLI и
локальная конфигурация GigaChat. Только нажатие «Создать презентацию» запускает обработку с передачей текста и
текстовой структуры шаблона в GigaChat. Сырые ответы и логи сервисов в браузер не выводятся.

На широком экране материалы и слайды открыты рядом. В узком окне переключайтесь между
вкладками «Материалы» и «Слайды»; после сборки открываются слайды готовой презентации.
Загрузка шаблона и открытие примера не переключают вкладку. При запуске генерации
автоматически открываются «Слайды» с анимацией сборки.
Во время загрузки и генерации на холсте проигрывается анимация слайдов с текущим этапом
обработки. Её можно приостановить или переключиться на просмотр шаблона. При завершении
или ошибке анимация останавливается; системная настройка уменьшения движения учитывается.
Статус генерации отдельно показывает анализ текста, составление плана, обработку конкретного
слайда и проверку содержания. Если модели нужно повторить запрос, это отражается в статусе.
При остановке интерфейс различает неподходящий формат ответа, ошибку проверки текста,
превышение времени, отказ доступа и проблему соединения. Подробная диагностика сохраняется
локально в `job.log` внутри временного каталога задания до остановки сервера; через HTTP
этот файл недоступен, сырые ошибки и ответы модели в интерфейс не передаются.

В одной сессии выполняется одна генерация за раз. Файлы хранятся во временном каталоге
до остановки сервера; перед остановкой скачайте результат. При обновлении страницы текущая
сборка восстанавливается в этой же вкладке. Текст формы и выбранный шаблон при обновлении
страницы не сохраняются. Сервер ограничивает сессию 30 загруженными шаблонами и 50 запусками;
PPTX должен содержать 1–250 слайдов и хотя бы один текстовый заполнитель.

## Требования к шаблону

- Формат — `.pptx`.
- Для генерации нужны существующие текстовые placeholders.
- Каждый выбранный слайд шаблона используется не более одного раза.
- Итоговый порядок соответствует плану content-service, а не исходному порядку шаблона.
- Если исключаемые слайды входят в PowerPoint custom show или section, builder завершится
  понятной ошибкой: безопасное обновление этих presentation-level ссылок пока не реализовано.

Парсер учитывает наследование размера и гарнитуры шрифта из абзаца, макета, образца и темы.
При известном размере шрифта вместимость текстового поля оценивается по его геометрии;
короткая подпись в образце не задаёт лимит всего поля. Если размеры неизвестны, используется
прежняя оценка по длине образца. Это эвристика, поэтому визуальная проверка остаётся важной.
Для заголовков учитываются соседние элементы переднего плана: текст и таблицы ниже, изображения
или фигуры справа могут уменьшать доступную область. Фон и элементы позади заголовка
не ограничивают её. Оценка общего числа символов не заменяет измерение отдельных длинных
слов выбранным шрифтом.

Builder сохраняет геометрию и оформление выбранных слайдов, заменяя текст placeholders.
Строки многострочного list-контента записываются отдельными PowerPoint-абзацами и получают
маркеры из шаблона. В быстром режиме однозначный маркер перед словом (`-`, `–`, `—`,
`*`, `•`) снимается до проверки, без изменения слов и переносов строк. Знаки перед
числами или валютой, `+`, нумерация и пустые пункты не исправляются таким способом;
оставшиеся ошибки отправляются на retry. Пользовательская разметка не изменяется.
Новые слайды, повторное клонирование одного образца, обычные text boxes, изображения и таблицы
как генерируемые слоты пока не поддерживаются.

## Прямой запуск этапов

У каждого сервиса есть CLI с явными путями:

```bash
cd services/parsing-service
uv run python -m app.main --help

cd ../content-service
uv run python -m app.main --help

cd ../builder-service
uv run python -m app.main --help
```

Обычный пользовательский сценарий должен идти через корневую команду `python -m exposlides`.

Для разработки сетевого режима отдельно сгенерируйте gRPC-модули из корня репозитория:

```bash
uv run python -m grpc_tools.protoc -Iproto \
  --python_out=services/parsing-service --grpc_python_out=services/parsing-service \
  proto/file_service.proto proto/parser_service.proto
uv run python -m grpc_tools.protoc -Iproto \
  --python_out=services/content-service --grpc_python_out=services/content-service \
  proto/file_service.proto proto/content_service.proto
```

Эти модули исключены из Git и не нужны для локальной файловой цепочки.

## Проверки разработки

```bash
uv lock --check
uv run ruff check .
uv run pytest
```

Тесты полностью офлайн: LLM подменяется детерминированными реализациями. E2E-тест создаёт
PPTX программно, проводит его через parser, настоящий LangGraph с fake LLM и builder, затем
повторно открывает результат и проверяет порядок, текст и стили.

## Сравнение качества генерации

Фиксированные сценарии и scorer находятся в `evals`. Пример оценки сохранённого ответа:

```bash
uv run python evals/score.py quarterly-results generated_content.json
```

Метрики и правила сопоставимого сравнения версий описаны в
[`evals/README.md`](evals/README.md). Scorer не заменяет редакторскую и визуальную проверку.

## Статус проекта

Рабочий локальный MVP замыкает файловую цепочку `PPTX → JSON → LLM → PPTX`. API gateway,
Kafka, protobuf, Docker/Compose и автоматическая визуальная evaluation остаются roadmap.
Датированный разбор архитектурных ограничений находится в
[`PROJECT_REVIEW.md`](PROJECT_REVIEW.md).
