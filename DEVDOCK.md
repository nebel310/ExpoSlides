### Этап 1. Завершение parsing-service (готова mvp реализация)
**Цель:** получать из шаблона полную структуру, дизайн-систему и классифицированные слайды, готовые для генерации контента и сборки.

**Шаги:**
1. Добавить классификацию типов слайдов (на основе layout_name, placeholder_type, расположения элементов)
2. Извлечь информацию о макетах (slideLayouts, slideMasters) – список доступных макетов, их placeholder'ы, позиции
3. Извлечь тему презентации: цвета темы, шрифты (major/minor), размеры шрифтов из master/layout
4. Для каждого слайда привязать его к конкретному layout (по имени или структуре)
5. Добавить извлечение фонов (цвет, изображение) слайдов и layout'ов
6. Добавить извлечение placeholder'ов с их типами и наследованием стилей
7. Протестировать на всех 3 предоставленных шаблонах, сверить JSON
8. (Опционально) Поддержка PDF: парсинг через pdfplumber/PyMuPDF, извлечение текста, изображений, координат; классификация по геометрии

**Результат:** сервис, который по файлу шаблона возвращает полную модель `Presentation` с `LayoutInfo`, `ThemeInfo`, `SlideClassification`.

### Этап 2. Реализация content-service
**Цель:** на основе скрипта доклада и структуры шаблона сгенерировать текстовый контент для каждого слайда.

**Шаги:**
1. Спроектировать вход/выход: вход – `Presentation` (JSON), скрипт (текст или размеченный JSON), настройки сложности; выход – словарь `slide_index -> текст для каждого placeholder/элемента`
2. Подключить LLM через LangChain (или напрямую OpenAI-compatible API)
3. Написать промпт для анализа скрипта: выделить смысловые блоки, тезисы, ключевые сообщения
4. Написать промпт для планирования: сопоставить смысловые блоки с типами слайдов из шаблона, определить порядок
5. Написать промпт для генерации текста под каждый конкретный слайд, с ограничениями по длине (не более X символов на placeholder, соответствие стилю)
6. Реализовать цепочку LangChain (или LangGraph) с возможностью параллельной генерации для слайдов
7. Учесть пользовательскую разметку скрипта: если пользователь явно указал, какой текст на каком слайде, строго следовать этому
8. Добавить валидацию сгенерированного контента (проверка на полноту, отсутствие галлюцинаций)
9. Протестировать на тестовых скриптах и шаблонах

**Результат:** сервис, который принимает структуру шаблона и скрипт, возвращает заполненный словарь контента.

---

### Этап 3. Реализация builder-service
**Цель:** из исходного шаблона и сгенерированного контента собрать готовый PPTX/PDF.

**Шаги:**
1. Получить исходный файл шаблона (из file-service или локально)
2. Открыть шаблон через python-pptx
3. Пройтись по слайдам и для каждого слайда:
   - найти соответствующий placeholder'ы по индексу/типу
   - заменить текст, сохраняя стили (шрифт, размер, цвет)
   - проверить, не выходит ли текст за границы рамки (расчёт высоты текста)
   - если выходит, уменьшить кегль или обрезать (по стратегии)
4. Если контент требует больше слайдов, чем есть в шаблоне, клонировать нужный layout и создать новый слайд по образцу (повторить структуру)
5. Поддержать добавление изображений/иконок, если они указаны в контенте
6. Сохранить итоговый файл в формате PPTX
7. (Опционально) Конвертировать в PDF (LibreOffice headless)
8. Вернуть путь к готовому файлу

**Результат:** сервис, который по шаблону и контенту создаёт валидный PPTX, готовый к скачиванию.

---

### Этап 4. Реализация evaluation-service
**Цель:** убедиться, что сгенерированная презентация качественная.

**Шаги:**
1. Реализовать программные проверки:
   - выход текста за границы рамок
   - пересечение элементов
   - пустые слайды или пустые placeholder'ы
   - соответствие количества слайдов плану
2. (Опционально) Рендерить слайды в изображения (LibreOffice) и анализировать:
   - CV-модель для детекции перекрытий/обрезок
   - LLM-оценка визуального качества (скриншот -> описание проблем)
3. Возвращать отчёт с оценкой (OK/проблемы)
4. Если проблемы – инициировать повторную генерацию (цикл)

**Результат:** сервис, который проверяет готовую презентацию и сигнализирует о проблемах.

### Этап 5. Реализация file-service
**Цель:** централизованное хранение входных и выходных файлов.

**Шаги:**
1. Подключить MinIO (объектное хранилище)
2. Реализовать API загрузки файла (получить bucket/key)
3. Реализовать API скачивания (отдать файл по key)
4. Хранение метаданных задачи (в БД или в MinIO metadata)
5. Очистка временных файлов

**Результат:** сервис, который управляет файлами.

---

### Этап 6. Реализация api-gateway
**Цель:** единая точка входа для фронтенда.

**Шаги:**
1. Создать FastAPI приложение
2. Эндпоинт `POST /upload` – загрузка шаблона и скрипта, сохранение в file-service, создание задачи
3. Эндпоинт `POST /generate` – запуск пайплайна (синхронно для MVP)
4. Эндпоинт `GET /status/{task_id}` – статус задачи
5. Эндпоинт `GET /download/{task_id}` – скачать готовый файл
6. Проксирование запросов к нужным сервисам (на первых порах REST, потом gRPC)
7. Swagger/OpenAPI документация

**Результат:** REST API для фронтенда.

### Этап 7. Оркестрация (Kafka + gRPC)
**Цель:** сделать систему асинхронной, масштабируемой, готовой к production.

**Шаги:**
1. Поднять Kafka (KRaft) в docker-compose
2. Определить топики: `template.uploaded`, `content.generated`, `presentation.built`, `evaluation.done`, `error.*`
3. Создать gRPC контракты в папке `proto/`:
   - `parsing.proto`
   - `content.proto`
   - `builder.proto`
   - `evaluation.proto`
   - `file.proto`
4. Реализовать gRPC серверы в каждом сервисе и клиенты для взаимодействия
5. Перевести api-gateway на gRPC для внутренних вызовов
6. Использовать Kafka для долгих операций: api-gateway публикует событие, сервисы подписываются, обрабатывают, публикуют результат
7. Настроить мониторинг (логи, метрики)

**Результат:** полноценная микросервисная архитектура с асинхронной обработкой.
